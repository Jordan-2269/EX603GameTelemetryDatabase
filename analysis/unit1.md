Modeling Justification
Every primary key in this schema is a surrogate integer (player_id, match_id, participant_id, game_mode_id), except for match_modes, which uses a composite key. I chose surrogate keys over natural keys like display_name or match_name because natural attributes can change over time (a player might rename themselves) or collide (two matches could share a name), and neither should be allowed to break every foreign key that points to them. Surrogate integers also keep joins cheap, which matters here since match_participants is the high-volume fact table that everything else joins against. The one exception, match_modes, deliberately uses a composite primary key over (match_id, game_mode_id) rather than adding its own surrogate id. That composite key isn't just an identifier, it's also the constraint that prevents the same match from being tagged with the same mode twice. Adding a surrogate key on top would mean enforcing that uniqueness rule separately, which is redundant when the natural composite already does the job for free.

The ON DELETE behaviors split along a clear line: CASCADE where the child row has no meaning without its parent, and RESTRICT where deleting the parent would silently destroy data other parts of the system still depend on. match_participants.match_id and match_modes.match_id both CASCADE, because a participation record or a mode tag only exists in the context of a specific match; once the match is gone, those rows are meaningless clutter. By contrast, match_participants.player_id and match_modes.game_mode_id both RESTRICT. Player participation rows feed leaderboards and aggregate statistics, so deleting a player shouldn't be allowed to quietly wipe out historical match results; the system should force an explicit decision, like anonymizing the player, rather than losing analytics data as a side effect. The same logic applies to game_modes: it's a reference/catalog table, and letting someone delete a mode that's still actively tagged on matches would corrupt historical categorization silently.

I chose to enforce structural rules in the schema itself rather than trusting the application layer: primary key uniqueness, NOT NULL on required display fields (display_name, match_name, mode_name), the composite uniqueness on match_modes, and all four foreign key relationships. These are the rules that must never be violated regardless of which client writes the data, whether that's a game server, an admin tool, or a batch import job, so putting them in the database is the only way to guarantee they hold everywhere. What I deliberately left to the application layer are business rules that are more situational or likely to change, such as whether a score is plausible for a given game mode, or whether a match's duration falls within an expected range for its type. Those rules depend on game-specific logic that evolves faster than the schema should, and encoding them as rigid database checks would make the system brittle every time gameplay balance changes.

Reflection
One decision a different designer could reasonably challenge is modeling matches and game_modes as many-to-many through the match_modes junction table, rather than giving matches a single game_mode_id foreign key. In many telemetry systems, a match really does belong to exactly one mode, and a simple one-to-many relationship would be simpler to write and query, no extra join required just to find a match's mode.

I kept the many-to-many design because game telemetry systems tend to tag matches with overlapping labels rather than one exclusive category. Something can be simultaneously "ranked," a specific map rotation, and a limited-time event mode, and analysts frequently need to filter or aggregate by any combination of those tags. A single foreign key column can't express that without ugly workarounds, while the junction table handles it cleanly and lets the mode taxonomy expand without any schema changes.

The tradeoff is read complexity: every mode lookup now needs a join instead of a direct column read. But since match_participants already forces joins for virtually every meaningful analytics query in this system, that extra join is a small cost against the flexibility of not having to redesign the schema every time the game adds a new kind of tag.
